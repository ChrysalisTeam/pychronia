PYCHRONIA README
#############################


Prerequisites
=================

- You need to have Python 3.11+ installed on your system
- Setup and activate a python3 virtual environment, if you wish

- On a debian/ubuntu, install additional dev files:

     $ sudo apt-get install python python-dev python-pip libjpeg8-dev libmysqlclient-dev"

- Checkout the repository to your system with GIT, or download/extract it as a zip

- "uv sync" (or BOOTSTRAP.py, see below) installs the project itself in editable mode, so the repository root and its "vendor/" folder (patched or unmaintained third-party packages) are importable from anywhere, no PYTHONPATH setup is needed


Installing dependencies and creating game DBs
==============================================

Python dependencies are declared in "pyproject.toml" and pinned in "uv.lock", they are installed with uv (https://docs.astral.sh/uv/).

The quick way to setup the engine is to launch "python BOOTSTRAP.py" from the root of the depot, with the python executable of your virtualenv.

If no errors occur (except some deprecation warnings), then the game portal is ready for use.

Else::

	Install the dependencies into your own virtualenv (by default, uv would create a ".venv" folder instead):

	$ export UV_PROJECT_ENVIRONMENT=/path/to/your/virtualenv     (on windows: set UV_PROJECT_ENVIRONMENT=C:\path\to\your\virtualenv)
	$ uv sync --frozen --inexact

	Or, if your virtualenv is activated:

	$ uv sync --active --frozen --inexact

	"--inexact" keeps the other packages already installed in your virtualenv.
	Add "--extra cms" to also install the (currently broken) Django-CMS dependencies of the "pychronia_cms" package.
	Use "uv lock --upgrade-package <name>" to upgrade a pinned dependency.

	Then reset both the SQL DB and the Zope Object DB of the game portal, with the "reset_django" and "reset_zodb" management commands described below.

The Django-CMS app, located in "pychronia_cms" package, behaves like a quite standard Django application, in development mode you can setup its databases and run a test server via the "pychronia-cms" command (eg. "uv run pychronia-cms runserver 8001").
So the remaindee of this doc focuses on the non-standard "pychronia_game" package.


Settings and dev commands
===========================

Settings of both sites live in the "config/settings/" package (see its __init__.py): "game.py" and "cms.py" for each site, "game_dev.py" and "cms_dev.py" for dev servers with persistent DBs, "game_test.py" and "cms_test.py" for throwaway test DBs, "e2e.py" for browser tests.

The "pychronia-game" and "pychronia-cms" commands, installed by "uv sync", are django-admin equivalents using the DEV settings of their site, unless a "--settings" option is given::

    uv run pychronia-game runserver
    uv run pychronia-cms runserver 8001
    uv run pychronia-game check --settings=config.settings.game_test

Machine-specific values of dev settings (eg. your local MariaDB DBs) go in untracked env files at the root of the repository, see ".env.example": ".env" for values of both sites, and optionally ".env.game" / ".env.cms" for values of a single site (they take precedence over ".env"); Python-level overrides go in untracked "config/settings/local_game.py" and "config/settings/local_cms.py" modules.

The "manage.py" scripts of "tests/" folders are equivalent to these commands, and the former settings modules ("pychronia_game.common_settings", "pychronia_game.tests.persistent_mode_settings"...) are deprecated aliases of the new ones.


Code style
=============

Python code is linted and formatted with ruff (configured in "pyproject.toml", installed with the "dev" dependency group)::

    uv run ruff check .        # add --fix to apply safe fixes
    uv run ruff format .

Pure reformatting commits are listed in ".git-blame-ignore-revs"; run "git config blame.ignoreRevsFile .git-blame-ignore-revs" once, so that "git blame" skips them.


Regenerating CSS files
=======================

If you modify SCSS files (used by both game portal and django-cms), you'll have to recompile them with pyScss.

See pychronia_common/static/MetalRadiance/build.bat for related commands.


Utilities and servers
========================

Besides standard django commands (runserver, migrate...), "pychronia-game" offers these pychronia_game management commands (see "--help" of each)::

    uv run pychronia-game reset_django     # DEV ONLY: migrate, then flush, the SQL DB (users, sessions...)
    uv run pychronia-game reset_zodb       # DEV ONLY: wipe the object DB (game data) and create a "DEMO" game instance
    uv run pychronia-game pack_zodb_file   # pack a local ZODB file, in case it gets too heavy (server must be stopped)
    uv run pychronia-game runserver

The reset commands ask for confirmation, and display the DB they're about to wipe; to experiment with them, use throwaway DBs via "--settings=config.settings.game_test".

The demo game which gets created, is by default filled with the content of "pychronia_game/tests/test_game_files/game_initial_data.yaml", and then altered by the GAME_INITIAL_FIXTURE_SCRIPT() function if it exists in settings.

You may modify GAME_FILES_ROOT and GAME_INITIAL_DATA_PATH settings to point respectively to a different tree of game assets, and a different yaml fixture file (or list of folders/files).

Maintenance commands, used by "bin/daily_game_maintenance.sh" in production: backup_all_games, check_global_sanity, reset_demo_account, notify_novelties_by_email.
Other tools: dump_initial_game_yaml (initial game data, eg. for murder-party sheet generators), extract_reusable_bits_from_game (message templates of a game instance).

When dev server is launched, the test game instance (created by "reset_zodb") can be reached at "http://localhost:8000/DEMO/"

**Game master credentials are the "master_login" and "master_password" fields of your game data "global_parameters". They are master/ultimate by default, in test fixtures.**

..note::

    Note that the "manage.py" file at depot root expects a PROD setup (see below); in dev environment, you won't need it.


Production deployment
========================

Production sites are installed with "uv sync" ("uv sync --extra cms" for the CMS), and configured by untracked env files at the root of the checkout (see the "PROD SERVERS ONLY" section of ".env.example"). DJANGO_SETTINGS_MODULE picks the site: "config.settings.prod_game" or "config.settings.prod_cms".

- With one checkout per site, everything can go in its ".env" file, DJANGO_SETTINGS_MODULE included.
- With both sites in the same checkout, site-specific values (SECRET_KEY, ALLOWED_HOSTS, SITE_DOMAIN...) go in ".env.game" and ".env.cms", shared ones (emails, cache...) in ".env", and DJANGO_SETTINGS_MODULE must be set by the web server config and the crontab (eg. "DJANGO_SETTINGS_MODULE=config.settings.prod_game bin/daily_game_maintenance.sh").

- The WSGI application is "config.wsgi:application" (the legacy "pychronia_launcher.wsgi" file is equivalent).
- The root "manage.py" and the "bin/daily_*_maintenance.sh" scripts (to be launched from the root of the checkout) use the same settings.
- Python-level overrides (eg. PASSWORDS_POOL or ACAPELA_CLIENT_ARGS of the game) go in an untracked "config/settings/local_game.py" or "config/settings/local_cms.py".

Without DJANGO_SETTINGS_MODULE, these entry points fall back to a legacy "pychronia_settings.py" module at the root of the checkout.


Special support for Chrysalis RPG
============================================

There is specific tooling to load the "Chrysalis" RPG campaign (https://chrysalis-game.com/fr/cms/). 

If the game data repository of this RPG is stored in a "Chrysalis/" folder which is sibling with the root folder of your Pychronia repository, then it'll be automatically detected,
and the `generate_auction_settings()` or `generate_mindstorm_settings()` functions can be used to automatically setup the game in either murder-party or alternate-reality-game mode.

These functions expect the root folder of the Chrysalis repository, which has one folder per game (with its scenario sources in a "scenario_fixtures/" subfolder). GAME_FILES_ROOT must then point to the "alternate_reality_game_auction/" folder of this repository, whose media are shared by both modes; `get_chrysalis_game_files_root()` computes this path.

Each of these functions returns a (GAME_INITIAL_DATA_PATH, GAME_INITIAL_FIXTURE_SCRIPT) pair. To let game creators choose the scenario of each new game instance (in /administration, alongside the game language), set GAME_SCENARIOS to a {scenario_id: (data_path, fixture_script)} dict instead, eg. `GAME_SCENARIOS = generate_chrysalis_scenarios(chrysalis_data_dir)`, which proposes "auction" and "mindstorm". GAME_DEFAULT_SCENARIO (else the first scenario) is used for instances created before scenarios existed. Without GAME_SCENARIOS, a single "default" scenario uses GAME_INITIAL_DATA_PATH and GAME_INITIAL_FIXTURE_SCRIPT, and the scenario field of the creation form is hidden. Like the language, the scenario of a game instance can't be changed afterwards.

See "config/settings/game_dev.py" for more information.


Launching game tests
=======================

Tests are run with pytest and pytest-django (both in the "dev" dependency group of uv), against throwaway databases: an in-memory sqlite test DB, and a ZODB file in a temp folder. From the repository root::

    uv run pytest                                  # unit tests of pychronia_game/tests/ (the e2e/ subfolder is excluded)
    uv run pytest pychronia_game/tests/test_game.py -k TestDatamanager -vl

pytest-django sets Django up with "config.settings.game_test", via the "--ds" option of [tool.pytest.ini_options] in pyproject.toml, which has precedence over a DJANGO_SETTINGS_MODULE environment variable. The SQL test DB is created once per run, and each test of BaseGameTestCase (a django.test.TestCase) runs in a rolled back SQL transaction, while its setUp() wipes and recreates the ZODB. Other tests needing SQL access must use the "django_db" mark (pytest-django blocks DB access otherwise).

The Playwright end-to-end tests have their own settings ("config.settings.e2e") and pytest.ini, so they must be launched separately (see pychronia_game/tests/e2e/README.md)::

    uv run pytest pychronia_game/tests/e2e

As a safety net, both suites refuse to start (in pytest_configure() of their conftest.py) if their settings use non-throwaway databases, eg. if given "--ds=config.settings.game_dev": tests wipe the ZODB and the SQL DB.

See https://docs.pytest.org/en/stable/how-to/usage.html and https://pytest-django.readthedocs.io for more usage info.


Managing games as a super admin
=================================

First use "uv run pychronia-game createsuperuser" to create a standard django admin account.

Then sign in via the dev server at http://localhost:8000/admin/

Now you can manage the different pychronia games at http://localhost:8000/administration/


Sources Tree Overview for pychronia_game package
===================================================

Most of the *pychronia_game* package consists of standard django components, and other common python modules:

- urls.py: django url routing files
- context_processors.py: add common game info in HTML template contexts
- forms.py: django declarative web forms
- middlewares.py: django middlewares, for pre and post processing of request
- models.py: required by django, but empty here (we don't use django's SQL ORM for our data)
- locale/: standard gettext files, for site translation
- template/: standard django templates
- templatetags/: custom django template tags and filters
- tests/: unit-tests and web-tests for the site
- utilities/: misc. data types and handy functions
- views/: not standard django function-views, these are similar to django class-based
  generic views: "GameView" classes that must be instantiated on each request, and that perform a lot of work ;
  some of these gameviews are "abilities", that are linked more closely to the datamanager, in which they have
  a private storage area - they actually behave as "extensions" of the datamanager.

Pychronia adds to these standard entries some layers dedicated to the game system:

- authentication.py: utilities to log in and out as a character or game master
- common.py: centralizes most useful variables of the application, to be imported as "from pychronia_game.common import *"
- default_game_settings.py: mainly a good reminder of available pychronia_game settings (django settings of the site are in "config/settings/game.py")
- menus.py: dynamically builds nested menus for the page, depending on the permissions of the current user
- datamanager/: dynamic stack of classes, designed to wrap a ZODB and expose tons of getter/setter/utility methods, as well as powerful class-based views
- scripts/: scripts to help maintain a pychronia_game deployment


Summary of HTTP request processing in pychronia_game
========================================================

When a HTTP request reaches the site, the following tasks are performed:

- pychronia_game middlewares determine which instance of the game is concerned
- they attach to the request a proper datamanager instance, perform user authentication, and process pending tasks that might remain (delayed actions, email sendings...)
- the targeted GameView is instantiated, and called with the request object as parameter
- the GameView performs access checks, returning HTTP error responses if needed
- depending on the kind of request (ajax or not), and the presence (or not) of POST data, the GameView modifies the content of the datamanager (via its public API) according to game rules, and action mixins
- the json or html response is built with templates and their associated data contexts
- middlewares perform some cleanup, and the response is returned to the user


Development tips for pychronia_game
======================================

- Only *persistent* versions of mutable types should be stored into the ZODB
  (and this is enforced by pychronia_game's checking system),
  so use Persistent subtypes instead of standard lists/dicts/sets.
- Regarding persistent objects: do NOT use PersistentMapping.copy() since it marks data as changed, and copy.copy() might cause troubles by copying object ZODB-IDs ; so use utilities.safe_copy(), or dict()/list() constructors, instead.
- All public methods of the datamanager must have a decorator (readonly_method, transaction_watcher...)
  to take care of ZODB transactions, depending on whether it may modify content or not.
- If webdesign gets broken, ensure you have well your {% extends %} tags at the TOP of your template
- Gameviews offer a powerful API to process forms, and turn them into method calls - no need to manually validate forms anymore.
- *register_view()* can be used to turn a standard django view into a GameView.
- An old Django debug toolbar might require a fix in django core/handlers/base.py to work with custom urlconfs::
  SEE https://code.djangoproject.com/ticket/19784#ticket
  More generally, django debug toolbar doesn't play well with our ZODB use, so you'd better keep it deactivated
- if layout gets screwed up in Chrome (a vertical spacing before the anthropia header, "&#65279;." appearing in web debugger), it's probably due to Byte Order Marks in html templates - just remove them.
